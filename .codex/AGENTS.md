# 차록다록 디자인 하네스

## 목적과 완료 기준
- Codex에서 차록다록 디자인 작업을 수행한다.
- 실행 입력은 PRD 변경 내용과 레퍼런스다.
- 실행자와 최종 승인자는 디자이너 본인이다.
- 핵심 화면 5종을 피그마로 제작하고, 필수 자동 검사
  실패 0건·보류 0건과 사람 승인을 확보한 뒤
  개발자 전달용 산출물을 준비하면 작업 완료다.
- 실제 개발자에게 전달하는 일은 디자이너가 한다.

## 기준 문서
- docs/prd.md: 서비스 요구사항
- docs/design.md: 시각 디자인 기준
- docs/story-service.md: 서비스 목적과 위반 금지 기준
- docs/story-work.md: 실제 작업 경험
- harness/r2-purpose.md: 하네스 목적
- harness/r3-pipeline.md: 단계별 입출력
- harness/r4-artifacts.md: 파일 구성·이력·재개
- harness/r5-gates.md: 게이트와 실패 처리
- harness/r6-roles.md: 역할·권한·트리거
- harness/r7-orchestrator.md: 실행 통제
- harness/r8-validation.md: 검증과 리뷰

서비스 스토리는 판정 기준으로, 작업 스토리는 작업 흐름의
근거로 사용한다. 둘을 혼합하지 않는다.

문서가 충돌하면 해당 위치와 결정할 항목을 제시하고
관련 작업을 보류한다. 임의로 기준을 변경하지 않는다.

## 실행 전 확인
- 필수 문서와 요청 범위를 확인한다.
- 해당 단계에 필요한 도구의 접근 가능 여부를 확인한다.
- 피그마 편집 전 대상 파일·페이지를 확인한다.
- 누락된 정보는 질문하고 해당 작업을 보류한다.
- 입력 확인과 G3의 최종 사람 승인은 구분한다.
- 규칙·스크립트·도구가 준비되지 않았으면
  검사를 실행한 것으로 간주하지 않는다.

## 실행 순서
1. 레퍼런스 수집·분석
2. G1 자동 검사
3. 화면 구조 설계
4. 디자인 규칙 정의
5. G2 자동 검사
6. 피그마 화면 제작
7. 최종 검토
8. G3 자동 검사 및 디자이너 승인
9. 개발자 전달 문서 확정

게이트가 실패 또는 보류이면 다음 단계로 넘어가지 않는다.

## 역할과 편집 범위

| 역할 | 편집 가능한 폴더 |
|---|---|
| 레퍼런스 분석자 | harness/artifacts/01-references/ |
| 화면 설계자 | harness/artifacts/02-structure/ |
| 디자인 규칙 작성자 | rules/ |
| 피그마 제작자 | harness/artifacts/04-design/ |
| 전달 문서 작성자 | harness/artifacts/05-review/ |

- 작업 에이전트는 담당 폴더만 편집한다.
- docs/와 다른 역할의 산출물은 읽기 전용이다.
- 다른 영역의 수정은 담당 역할에 요청한다.
- 피그마 제작자는 지정한 외부 파일·페이지만 편집한다.
- 전달 문서 작성자는 handoff.md만 편집하며
  report.json을 수정하지 않는다.

### 읽기 전용 판정자
- 판정 스크립트를 실행하고 근거를 확인한다.
- 산출물과 규칙을 수정하지 않는다.
- 규칙 ID, 통과·실패·보류, 근거, 복귀 단계를 반환한다.

### 오케스트레이터
- 역할 호출, 실행 순서, 게이트, 재시도, 승인 요청을 관리한다.
- 다음 관리 데이터만 기록한다.
  - harness/artifacts/run-state.json
  - harness/artifacts/history/의 실행 이력
  - harness/artifacts/05-review/report.json
- 작업 산출물과 규칙을 직접 수정하지 않는다.
- 판정 결과를 임의로 통과로 변경하지 않는다.

## 산출물
- 단계 1: harness/artifacts/01-references/references.json
- 단계 2: harness/artifacts/02-structure/screens.json
- 단계 3: rules/design-rules.json
- 단계 4: harness/artifacts/04-design/figma-manifest.json
- 단계 4: 같은 폴더에 검사용 추출 데이터와 화면 이미지
- 단계 5: harness/artifacts/05-review/report.json
- 단계 5: harness/artifacts/05-review/handoff.md

핵심 화면은 기록 목록, 차 기록 작성, 기록 상세,
내 취향 분석, 기록 항목 설정의 5종이다.
상태별 변형과 모달을 포함한 전체 프레임 수와 구분한다.

## 규칙의 단일 기준
- 스크립트는 rules/design-rules.json을 읽는다.
- 각 규칙에 고유 ID와 원문 근거를 기록한다.
- 원문 충돌·미확정 값·근거 부족은 보류한다.
- 의미 판단을 자동으로 확인할 수 없으면 통과로 간주하지 않는다.
- 수치·판정 규칙을 다른 파일에서 독립적으로 변경하지 않는다.

## 게이트

### G1 — 레퍼런스 분석 후
- 레퍼런스 1개 이상
- 출처 URL·참고 이유 누락 0건
- 공통 패턴마다 서로 다른 연결 레퍼런스 2개 이상

### G2 — 화면 구조와 디자인 규칙 정의 후
- 필수 화면 5종 누락 0건
- 화면 ID 중복·PRD 근거 누락 0건
- 규칙 ID 중복·원문 근거 누락 0건
- 규칙의 미확정 값·원문 충돌 0건
- 작성 화면의 필수 입력 필드 집합이 차 이름 1개와 일치
- 선택 항목의 표시·숨김 설정 누락 0건

### G3 — 최종 검토
- 필수 화면별 실제 피그마 노드 연결 누락 0건
- 검사용 데이터 추출 실패 0건
- 검사 대상 속성의 허용 토큰 위반 0건
- 피그마 추출 데이터에서도 G2의 서비스 조건 충족

필수 검사 실패 0건·보류 0건이어야 자동 통과한다.
피그마 추출 데이터가 없으면 보류한다.
디자인 검사는 화면 명세와 표현을 대상으로 하며,
실제 저장 동작은 구현 이후 검증한다.

### G3 사람 승인
다음 자료를 디자이너에게 제시한다.
- 핵심 화면 5종의 이미지와 피그마 링크
- 자동 검사 결과
- 미해결 항목 목록

다음 3항목을 각각 확인받는다.
- 브랜드색의 절제와 무채색 구성
- 참고 스타일과의 부합
- 시각적 가독성

자동 검사 통과와 3항목 승인 완료가 모두 필요하다.
사람 승인 지점은 G3의 1곳이다.
승인은 검토한 산출물 버전에 연결한다.

## 실패와 재시도
- 레퍼런스 근거 부족 → 단계 1
- 화면·요구사항 누락 → 단계 2
- 규칙 누락·충돌 → 단계 3
- 규칙과 화면 불일치 → 단계 4
- 수정 후 영향을 받은 후속 단계와 검토를 다시 실행한다.
- 자동 수정은 게이트별 최대 2회다.
- 이후에도 미통과이면 중단하고 원인과 필요한 결정을 보고한다.
- 사람 반려 시 사유를 기록하고 해당 단계부터 수정한다.

## 상태·이력·재개
- run-state.json에 단계 상태, 입력·규칙·산출물의 해시,
  검사 결과와 승인 기록을 저장한다.
- 변경 없는 완료 단계만 건너뛴다.
- 변경의 영향을 받는 단계부터 다시 실행한다.
- 변경된 산출물에 대한 이전 검사·승인은 무효화한다.
- 기존 결과는 harness/artifacts/history/ 아래 실행 ID별로 보관한다.

## 자연어 트리거
- “차록다록 디자인 시작”: 새 실행
- “이어서 진행”: 변경 여부 확인 후 재개
- “검토해줘”: 현재 산출물만 판정
- “승인”: 대기 중인 G3 요청에 제시된 버전 승인

승인 요청이 없으면 일반 대화의 “승인”을
G3 승인으로 기록하지 않는다.

## 검증과 완료 보고
- harness/r8-validation.md의 사례를 실행한다.
- 정상·위반·데이터 누락 사례의 기대 결과를 확인한다.
- 재개, 승인 무효화, 재시도 제한, 권한 차단을 검증한다.
- 각 사례의 ID·기대 결과·실제 결과·실행 여부·근거·
  기대 결과 일치 여부를 기록한다.
- 실행하지 않은 검사는 미실행으로 표시한다.
- 권한 제한은 실제 쓰기 차단 여부로 검증한다.
- 모든 필수 사례의 기대 결과가 일치해야 검증 완료다.
- 문서 승인, 구현 완료, 검증 완료를 구분해 보고한다.
